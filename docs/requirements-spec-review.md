# PSDリサイズ出力ツール — ドキュメントレビュー

レビュー対象: `requirements-spec.md`、`ui-sample.html`  
レビュー観点: 仕様の完全性・一貫性、実装への落とし込みやすさ、UIモックとの整合

---

## 総評

目的・対象外・入出力・リサイズ数式・配布想定まで一通り揃っており、実装・法務・販売の境界も意識されている。一方で、**優先順位の表記ゆれ**、**未決定事項と本文の関係**、**UIモックと仕様の細部の差**を詰めると、実装時の解釈ブレを減らせる。

## requirements-spec.md

### 強み

- **3.2 対象外**で Photoshop 互換やレイヤー再現の限界が明確で、スコープ管理に効く。
- **contain の数式と座標**がそのまま実装に落ちる。
- **§8.2 の優先順位**（画面指定 → 保存済み上書き → PSD）がユーザー操作と整合している。
- **§10** のエラー／警告の切り分けが実装・テスト設計に使いやすい。
- **§15** で Booth 想定の同梱物・ライセンス・更新の話まで書いてあり、プロダクトとして現実的。

### 指摘・改善提案

1. **§5.3 と §8.2 の「優先」の関係**  
   §5.3 は「マニュアル上書き → テンプレ PSD」、§8.2 は「画面 → 保存済み → PSD」の3段である。意味としては §8.2 が詳細で正しいはずなので、§5.3 に「詳細は §8.2 に従う」と一文あると、読み手が迷わない。

2. **§7 と §14 のはみ出し**  
   §7 は「警告を表示」とあり §14 は「禁止か警告のみか未決定」である。**初期方針は警告**と読めるので、§14 の該当箇所を「最終ポリシー（禁止にするか等）は未決定、初版は警告」と書き分けると矛盾が減る。

3. **単位の明示**  
   幅・高さは一貫して **px** と仮定しているように見えるが、§8 や §5.3 に「単位はピクセル（印刷所が mm 指定の場合は別途換算または手入力）」のような一文があると、マニュアルが物理寸法のみのケースでの解釈が固まる。

4. **解像度とピクセル寸法**  
   印刷では「350dpi で ○×○mm」と「ピクセル数」がセットで出ることが多い。**dpi だけ変えて px は変えない**のか、**dpi に応じて推奨 px を出す**のか、仕様レベルで一言あると UI（§9）と §8 のフィールド設計が揃う。

5. **§11「高品質なリサンプリング」**  
   アルゴリズム名は未確定でよいが、**縮小と拡大で同じ方式でよいか**、**ガンマ／線形**の扱いを将来議論するなら「品質目標」として1行あるとテスト観点が立つ。

6. **§14 と §5.1**  
   レイヤー構成が未決定のまま §5.1 に両案があるのは妥当だが、**受け入れ基準**（例: Photoshop で開いて1〜2レイヤー、背景が白）を §11 近くに短く書くと、§14 が閉じたときの完了条件が明確になる。

7. **内部リンク**  
   `§15 配布・販売仕様` のアンカーは Markdown レンダラによっては `#15-配布販売仕様booth想定` とずれることがある。利用するホスト（GitHub 等）で目視確認しておくとよい（必須ではない運用メモ）。

## ui-sample.html

### 強み

- **左：ファイル／上書き／情報／調整、右：プレビュー**は §9 と対応している。
- **上書きチェック・幅・高さ・dpi・テンプレ情報の3行**は §8・§9.2 の意図と一致。
- **警告ボックス**は §7・§10.2 の「はみ出し警告」の具体例になっている。
- 冒頭で **モックであること**を明示しており、誤解を防げる。

### 指摘・改善提案

1. **プレビューのアスペクト比**  
   コメントで「実装時はテンプレに合わせる」とある一方、モックは `3508/2480` 固定である。サンプルとして問題ないが、仕様書側に **「プレビューは出力キャンバスのアスペクト比に追従」** と書いておくと、モックと実装のギャップが説明しやすい。

2. **スライダーと §6 の対応**  
   拡大率は **contain 後の追加スケール**なのか、**キャンバスに対する絶対スケール**なのか、モックだけだと曖昧である。§7 に「手動の拡大率は、自動 contain 後の倍率（1.0 = 自動結果）」のような定義があると、UI と出力が一致しやすい。

3. **「containで再配置」が disabled**  
   モックとしてはよいが、§9.4 では操作項目として挙がっているので、**実装時は有効**である旨を HTML の `disabled` 近くのコメントで補足してもよい。

4. **アクセシビリティ**  
   数値入力の `<label>` が一部 `for` なしで、スクリーンリーダーでは項目名が弱くなる可能性がある。本番 UI 設計では `for` / `aria-labelledby` の統一を検討するとよい。

5. **サンプル警告の表示条件**  
   スクリプトは X/Y の閾値で警告の出し分けをしており、**拡大率だけでははみ出し警告が出ない**モックになっている。実装では「キャンバス境界との幾何判定」になるので、仕様書 §10.2 の「はみ出し」と定義を揃えておくとよい。

## 結論（レビュー結果）

- **承認しうる水準の要件定義**である。実装に入る前に、次の4点を短く追記または §14 で整理すると、本レビューの指摘はほぼ吸収できる。
  1. §5.3 と §8.2 の関係
  2. はみ出しの最終ポリシー（初版は警告、等）
  3. 寸法の単位・dpi と px の関係
  4. 手動スケール（拡大率）の定義

### 残論点・軽微な改善余地（必須ではない）

1. **§8.2 と「上書き」UIの対応**  
   画面上の「マニュアル上書き」チェックオフ時、幅・高さ・dpi の入力は **§8.2 の「ユーザーが画面上で指定」に入るのか、無効扱いで 2→3 に落ちるのか**が、読み手によって一文欲しくなる。オフ時は「保存済みまたはテンプレのみ参照」などと書けると実装とテストが揃いやすい。

2. **§7.3「中央揃え」と手動拡大率**  
   中央揃え時に拡大率を維持するか 100% に戻すかを実装委ねとしている。**§11.2 の回帰比較**（100%・オフセット 0）と組み合わせると、製品としてはどちらかに寄せた方がユーザー説明が楽になる可能性がある（現状でも仕様としては妥当）。

3. **§10.2 はみ出しの「有効範囲」**  
   全面透過 PNG 等、**アルファがすべて 0 の画素**のみの場合の外接矩形の扱い（0 サイズ扱いで警告なし、等）は未記載。稀だがサポート方針を一文あるとよい。

4. **アンカー URL**  
   冒頭注記どおり、`#43-座標系寸法の単位` 等はホスト依存。リリース前に主要ビューアでリンクを踏む運用で十分。
